# Android 本地 Git 空间维护

- 状态：`confirmed`
- 更新：2026-09-02

## 目标与边界

- 只缩减 Android 设备本地 `.git` 对象和引用，不修改表情工作区文件，不改写远端提交、分支、标签或提交 ID。
- 禁止 squash、force push、reset 远端、删除远端标签和 Git LFS 历史迁移；其他平台继续按完整 Git 历史正常 clone、fetch 和 checkout。
- App 本地不提供历史浏览；空间维护后只保证最近 5 个提交可离线访问，完整历史继续由远端保存。

## 新仓库克隆

- 克隆到现有同级暂存目录，固定使用远端默认分支、`depth=5`、单分支和不拉标签；协议校验成功后才原子切换为正式仓库。
- clone 失败继续删除暂存目录并保留未配置状态，不得留下半个浅仓库。
- 后续普通 fetch 可以从本地浅边界继续取得新提交；不得为了同步自动 unshallow。

## 空间统计与触发条件

- `worktreeBytes` 统计仓库工作区但排除 `.git`；`gitBytes` 只统计 `.git`；符号链接不跟随，统计失败不得触发维护。
- 自动维护条件为：仓库不是 shallow，或 `gitBytes > max(512 MiB, worktreeBytes × 1.5)`。
- 每次普通同步成功后只做轻量统计；满足条件时调度唯一维护任务。自动任务要求网络连接、充电、电量不低和存储空间不低。
- 设置页仓库区域显示工作区大小、Git 大小、完整/浅历史状态和最近维护结果，并提供“立即优化仓库”。手动入口仍在后台执行且要求网络连接，但不要求充电。

## 维护流水线

维护 Worker 必须在 `Dispatchers.IO` 中执行：

```text
重新执行普通同步
→ 确认 RepositoryState.SAFE 且工作区干净
→ 确认本地 HEAD 与 origin/当前分支完全一致
→ 仅 fetch 当前分支，设置 depth=5、NO_TAGS
→ 再次确认 HEAD 与远端跟踪分支一致
→ 严格校验真实表情协议
→ 使本地 reflog 和不可达对象立即过期
→ JGit 非 aggressive GC/repack
→ 重新校验仓库、协议、HEAD 和空间统计
```

- 任一前置条件不满足时跳过对象清理并保留全部本地数据；不能用 reset 或 checkout 消除本地修改。
- GC 不使用 aggressive 模式，避免在移动设备上产生过高 CPU、内存和临时空间峰值。
- GC 前要求可用空间至少为 `min(当前 Git 大小, 工作区大小) + 128 MiB`，用于先生成新 pack 再替换旧 pack；空间不足时安全跳过，不提前删除旧对象。
- 维护与普通同步共用同步锁，与 App 管理写入共用写入锁；App 和 QQ 只读路径继续使用最近有效快照，不等待维护。
- 成功后本地 fetch refspec 只保留当前分支并设置 `tagOpt=--no-tags`；该配置仅存在于 Android 本地仓库。
- 维护会删除 Android 本地的标签和当前 `origin` 下其他远端跟踪引用，使它们不再保留旧对象；远端标签和分支不受影响。若发现当前分支以外的本地分支则拒绝维护，不自动删除用户可能尚未推送的本地分支。

## 失败和恢复

- 只有普通同步已经成功推送后才允许收缩浅边界；因此被清理的历史对象始终仍存在于远端。
- depth fetch、配置保存、GC 或最终校验失败时记录完整脱敏日志和独立维护状态，不覆盖最近一次同步成功状态。
- JGit GC 先写新 pack 再替换旧 pack；异常时保留可读取的现有 pack。不得手工删除当前 pack、工作区或 `.git/objects` 未知临时文件。
- 维护失败不阻止表情读取、导入、发送和下次普通同步；后续满足约束时重试。

## 已验证容量基线

- 测试仓库完整历史 472 个提交：工作区约 224 MiB、`.git` 约 1.33 GiB、总计约 1.56 GiB。
- depth=20：`.git` 约 700 MiB、总计约 926 MiB，收益不足。
- depth=5 并清理 reflog/不可达对象：`.git` 约 223 MiB、总计约 450 MiB；远端历史和提交 ID未变化。

## 验收

1. 新 clone 的 `.git/shallow` 存在、只配置默认分支且不拉标签，协议和图片字节正确。
2. 完整历史仓库同步成功后可自动转为最近 5 个提交，空间明显下降；远端 refs 和所有历史提交不变。
3. 下一台完整 clone 仍能读取 472 个历史提交；浅仓库在其他客户端产生新提交后仍能 fetch、rebase 和 push。
4. 本地脏工作树、未推送提交、远端抢先更新、rebase 状态、协议损坏和网络失败均不得执行 GC。
5. 维护进行中 App 和 QQ 读取正常；失败后工作区和最近有效读快照不变。
