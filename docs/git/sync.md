# Git 同步

- 状态：`implemented`
- 更新：2026-10-10

## 引擎和边界

- Android 端使用 JGit。
- 上层只依赖 EmoRepo 自己的 Git 接口，不直接传播 JGit 类型。
- 每个仓库同一时间最多运行一个同步任务。
- 同步任务使用独立的同步互斥锁串行执行；仓库写入锁只串行化 App 管理写入、最近使用写入和 Git 的本地状态修改。App 与 QQ 的只读路径不得获取该锁，Git `status/add/commit/rebase`、冲突恢复或失败都不能阻塞已有内容读取。
- 所有 JGit 仓库打开、校验、克隆和同步只能从 `Dispatchers.IO` 或 WorkManager 后台线程调用；App 状态对象构造和 Compose 主线程不得调用 `Git.open()` 或等待 Git Future。
- 根索引、包内索引和最近使用读取采用原子文件的只读候选，并缓存最近一次完整解析结果。Git 中间态、冲突标记、文件替换窗口或写入失败时返回最近一次有效结果；Git 完成后的协议校验必须绕过缓存直接检查真实工作树，不能用旧缓存掩盖损坏。
- 不提供 pull-only 模式；每次同步都检查远端并在需要时 rebase。
- 不提供 Wi-Fi-only 条件。

## 触发器

| 事件 | 默认行为 |
|---|---|
| 新增、删除、移动表情 | debounce 后立即同步 |
| 修改索引、封面或顺序 | debounce 后立即同步 |
| 最近使用 CSV 变化 | 本地立即写入；同步延迟可配置，默认 30 分钟，`0` 表示每次使用后立即同步 |
| App 启动 | 执行一次同步 |
| 用户手动同步 | 立即执行 |
| 后台远端轮询 | 默认每 30 分钟执行，可配置或关闭；最低 15 分钟 |

不对使用记录同步设置 15 分钟下限：

- 延迟为 `0` 时，使用唯一 OneTimeWorkRequest 立即请求同步。
- 延迟大于 `0` 且不足 15 分钟时，使用带初始延迟的 OneTimeWorkRequest 合并记录。
- 只有与使用事件无关的周期远端轮询需要受 Android PeriodicWorkRequest 最低 15 分钟限制。

网络不可用时使用退避重试，不限制网络类型。

- 表情修改 debounce 默认为 10 秒，采用从最后一次成功修改重新计时的尾沿窗口。
- 使用记录正数延迟从第一条未同步记录开始计算固定窗口，后续使用不重置到期时间。
- 任何其他同步先发生时，一并刷新和提交尚未到期的使用记录。
- 仓库配置完成后，App 每次启动都请求同步。
- 单次任务失败最多自动重试 5 次，指数退避从 30 秒开始，上限 30 分钟；之后保留本地提交并在 App 内显示错误。

### 连续添加时的同步合并

- 状态：`implemented`；2026-10-10 用户在讨论后要求复现并修复，确认 10 秒尾沿防抖、面板队列隔离和不取消运行中同步的方案。JVM 和源码验证已通过，Android WorkManager 调度及 QQ 真机待验收。
- 图片和索引仍立即落盘；添加成功只以本地写入结果为准，不等待 Git 暂存、提交或上传。重复项或全部失败不重新计时。
- 防抖覆盖整个修改触发的 Git 流水线，不只推迟 `commit`。WorkManager 的网络约束和后台调度可能让实际启动晚于窗口到期。
- 修改发生时更新 App 私有持久化的修改代次和到期时间，不写入表情仓库。待执行任务在进入 Git 前重新检查最新到期时间，连续修改只合并成一轮同步。
- 已经运行的同步不得因新修改被取消或替换；运行期间的新修改最多保留一个待执行的后续任务。该任务仍检查最新防抖窗口，完成本轮开始后产生的修改；不能因唯一任务仍在运行而丢弃后续上传。
- 只有同步成功才确认本轮开始前的修改代次。同步期间的新修改不能被旧代次的完成标记清掉；失败沿用现有退避和重试上限。
- 仅已被成功同步覆盖的重复修改唤醒可以跳过 Git；App 启动、手动同步、最近使用和远端轮询保持原触发语义。
- 防抖期间进程退出不删除已落盘图片；持久化待执行任务和下次 App 启动同步负责继续上传。
- 不移除仓库写入锁，也不保证与已经开始的 Git 本地写入重叠的导入无需等待；本次修复保证这种等待不会继续堵住打开添加面板的入口。

## 流水线

每个触发器进入相同流水线：

```text
刷新待写入 JSONL/CSV
→ 检查本地变更
→ git add / commit
→ fetch 上游
→ 上游有新提交时 rebase
→ 结构化自动解决冲突并继续 rebase
→ 本地领先时 push
→ 重新加载仓库状态
```

仓库预检在 EmoRepo 仓库独占锁内执行。若仓库状态安全、现有 Git 索引可读取但残留 `.git/index.lock`，则记录恢复日志、删除陈旧锁并继续；仓库状态不安全或索引损坏时保留现场并停止，不得盲目删锁。

- 本地无变化时仍执行 fetch/rebase 检查。
- rebase 失败不得用 force push 或 reset 覆盖任一侧。
- push 失败保留本地提交，由下次同步重试。
- 同步失败或网络请求长期等待不能阻塞本地表情读取；状态和错误交给 App 展示，最近一次有效读缓存继续可用。fetch 期间发生的新本地修改必须在 rebase 前再次提交，避免带脏工作树进入 rebase；push 期间的新修改留给已调度的下一次同步。
- 普通同步不得在主流水线中直接执行耗时 GC。同步成功后按 [`storage-maintenance.md`](storage-maintenance.md) 统计并调度独立维护 Worker；维护 Worker 会再次同步并重新确认本地/远端一致，不能复用过期的成功结论。
- Git 作者名和邮箱由用户按仓库配置；缺失时禁止创建提交，但允许拉取更新。
- 默认提交信息为 `Update local emoticons`，允许用户配置。
